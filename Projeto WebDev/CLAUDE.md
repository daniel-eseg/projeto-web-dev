# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

An individual academic project (ESEG, Engenharia de Computação, Programação Web, 2nd semester 2026). The task is to modernize a legacy Oil & Gas management system ("Petróleo e Gás") whose data lives in a spreadsheet (`10_petroleo_gas.xlsx`, 8 sheets, 14,799 records) and turn it into a full-stack web app. The project brief is `../contextualizacao-projeto.pdf`. The requirements spec is `02_Levantamento_de_Requisitos.pdf`. All domain names, identifiers and docs are in Portuguese, so keep that convention.

**Mandatory stack (the grade depends on it):** Java, Spring Boot (Spring MVC, Spring Data JPA, Spring Security), a relational DB, JPA/Hibernate, HTML, CSS, Bootstrap, Thymeleaf. Thymeleaf must render data and forms bound to Controllers, and it can't be swapped for another view technology (no SPA/React or REST-only frontend). Features that are simulated, not persisted, or only visual don't count.

## Repository layout

The git repo root is `projeto-web-dev/` (remote `https://github.com/daniel-eseg/projeto-web-dev.git`, branch `main`). It contains the brief PDF and this `Projeto WebDev/` folder.

- `Projeto WebDev/*.java`, `petroleo_UML.asta`, `Class Diagram0.png`: Phase 3 artifacts generated by Astah (field-only stubs in the default package). They are the UML source of truth. **They are not compiled.** The real entities live in the Spring project.
- `Projeto WebDev/oilDynamics/oilDynamics/`: the Spring Boot application, built with **Maven** (`pom.xml` + `mvnw`). A Gradle version existed briefly and was removed, so don't reintroduce Gradle files. Spring Boot 4.1, `java.version` 21, Lombok, Bean Validation, H2, Thymeleaf + `thymeleaf-extras-springsecurity6`, devtools. Base package `br.edu.eseg.petrolifera.oilDynamics`.
  - `model/`: JPA entities mapped from the UML, with Bean Validation annotations (Portuguese messages), plus enums `StatusPoco` (which owns the RN-02 transition rule `podeMudarPara`), `StatusEntrega` and `Produto`.
  - `repository/`: Spring Data interfaces for all 8 entities, using derived queries. List queries use `@EntityGraph` to fetch associations shown in tables.
  - `service/`: business rules for Campo, Poço and Produção (uniqueness, RN-02 transitions, RN-03/04, RN-06 delete guard). A rule violation throws `RegraNegocioException(campo, mensagem)`, and a missing id throws `RegistroNaoEncontradoException`, which `TratamentoErros` turns into a 404 rendered with `erro.html`.
  - `controller/`: full CRUD for `/campos`, `/pocos` (supports `?status=` filter) and `/producoes`, following the same pattern: `GET` list, `GET /novo`, `GET /{id}/editar`, `POST /salvar`, `POST /{id}/excluir`, with post-redirect-get and flash messages. `ErrosFormulario` maps a `RegraNegocioException` onto the `BindingResult`, so the message shows next to its field. `/` redirects to `/campos`.
  - **Edit pattern:** a service never `save()`s the bound form object on update. It loads the managed entity and copies the editable fields, because merging a detached `Campo`/`Poco` with an empty collection would trigger `orphanRemoval` and delete its children. Keep this pattern for new entities.
  - Associations in forms are bound as `campo.id`, `poco.id` and `refinariaDestino.id`, and the service resolves them through the repository. An empty id means none.
  - `templates/`: `fragments/layout.html` (head, navbar, flash messages, footer) plus `campos/`, `pocos/`, `producoes/` (`lista.html` + `form.html`) and `erro.html`. `messages.properties` holds the type-conversion error messages.
  - `config/SecurityConfig.java`: provisional. Static files and `/h2-console/**` are public, everything else requires login, and there is a single dev user `admin`/`admin123` from `application.properties`. Roles come in phase 9.
  - `src/main/resources/static/css/style.css`: site stylesheet, loaded on top of Bootstrap 5.3.3 from the jsDelivr CDN.
  - Database: H2 file at `./data/oildynamics` (git-ignored), `ddl-auto=update`. If entity constraints change, delete `data/` so the schema is recreated. Console at `/h2-console` (JDBC URL `jdbc:h2:file:./data/oildynamics`, user `sa`, empty password). Tests use the in-memory H2 from `src/test/resources/application.properties`.
  - Not built yet: refinaria, venda, transporte, segurança ambiental and preço de mercado have repositories but no service, controller or screens, so the refinaria dropdown on the produção form stays empty until refinaria CRUD or the migration (RF-10) exists.
- Documents referenced in the spec but missing here: `01_Relatorio_Entrega1`, `05_Scripts/schema_proposto.sql` and the source spreadsheet. Ask the user for them instead of guessing their contents.

## Commands

Run from `Projeto WebDev/oilDynamics/oilDynamics/`. The `java` on PATH is 1.8, so point `JAVA_HOME` to a JDK ≥21 first (installed: `~/.jdks/corretto-22.0.2`, `~/.jdks/openjdk-27.0.1.0.2`).

```bash
export JAVA_HOME="$HOME/.jdks/corretto-22.0.2"   # Git Bash; in PowerShell: $env:JAVA_HOME="$HOME\.jdks\corretto-22.0.2"
./mvnw spring-boot:run                             # app at http://localhost:8080 (login admin / admin123)
./mvnw verify                                      # compile + all tests
./mvnw test -Dtest=StatusPocoTest                  # one test class
./mvnw test -Dtest=StatusPocoTest#paradoSoPodeIrParaManutencao   # one test method
```

## Domain model (see `Class Diagram0.png`)

- `Campo` 1—* `Poco` (composition). `Poco` 1—* `Producao` (composition).
- `Producao` → `Refinaria` (optional `refinariaDestino`). `SegurancaAmbiental` → `Poco` (optional).
- `MovimentacaoProduto` (abstract: produto, volume, data) is the superclass of `Venda` and `TransporteLogistica`. `TransporteLogistica` → `Refinaria` (`refinariaOrigem`) and aggregates into `Venda`.
- `Venda.calcularValorTotal` and `TransporteLogistica.calcularCustoTransporte` depend on `PrecoMercado` (at most one record per month).

How the JPA entities in `model/` differ from the Astah stubs (deliberate, justified by the requirements):
- Every entity has a surrogate `Long id` (IDENTITY). The legacy text ID (`CP0001`, `PO00001`, `RF001`…) becomes a unique `codigo` column (LA-01).
- `Poco.idCampo` and `Producao.idPoco` were removed. The `@ManyToOne` reference is the owning side and holds the FK (`campo_id`, `poco_id`).
- `MovimentacaoProduto` is a `@MappedSuperclass` (no table of its own). `Venda`/`TransporteLogistica` no longer redeclare `produto`/`volume`/date (LA-06). The shared date is the `data` field, in column `data_movimentacao`.
- Arrays became `List`. Compositions (`Campo→Poco`, `Poco→Producao`) use `cascade = ALL, orphanRemoval = true`. The `Venda→TransporteLogistica` aggregation has no cascade.
- Poço status, delivery status and produto are `@Enumerated(STRING)` enums. The other domains (ambiente, campo status, refinaria status, tipoPoco, gravidade, modal, mercado) are still `String`, because their valid values are open questions (V-02/V-05).
- Numeric fields use wrapper types (`Double`/`Integer`) so form binding can tell "empty" from 0.
- `uk_producao_poco_data` enforces RN-04 in the DB. Indexes exist on `poco.status_poco` and `producao.data_producao`.
- The calculation methods still return 0 (TODO RF-09) until the volume unit is decided (V-04).
- Single-field rules (required fields, non-negative values, efficiency 0–100, 2-letter UF) are Bean Validation annotations on the entity, so Hibernate also emits them as DDL constraints. Rules that need the database or the previous state (uniqueness, status transitions, poço must be Ativo, date ≥ poço start) live in the services.

## Business rules the implementation must enforce

Enforce these on the server (service layer plus DB constraints). Hiding them in the UI is not enough.

- **Poço status** ∈ {Ativo, Manutenção, Parado}. Allowed transitions: Ativo→Manutenção/Parado, Manutenção→Ativo/Parado, Parado→Manutenção only. Parado→Ativo must be blocked with a message (RN-01/02).
- **Produção**: the poço must be Ativo. The date must be ≥ the poço `dataInicio`. Only one produção per (poço, data). Volumes and costs must be ≥ 0, and efficiency must be 0–100 (RN-03/04/05).
- **Campo**: unique code, 2-letter UF, controlled `ambiente`/`status` domains. Deleting a campo cascades to its poços and produções, but is allowed only if none of its poços is Ativo (RN-06). Campo status goes Desenvolvimento→Produção→Declínio with no going back (RN-11, *to be validated*).
- **Produto** (venda and transporte) ∈ {Petróleo, Gás, GLP, Diesel, Gasolina}. Movement volume must be > 0 (RN-07/08).
- **Entrega status**: Em trânsito→Concluída/Atrasada, Atrasada→Concluída. Concluída is final (RN-09).
- **Months without a PrecoMercado quote**: the calculation returns a warning, not an error, and the venda is still saved (RN-10).
- **Profiles** (RN-12): `ADMIN` creates, edits and deletes campo/poço and deletes produção. `OPERADOR` can view and register produção. When OPERADOR opens the new-campo form or tries a delete, it must get HTTP 403.
- **Non-functional requirements**: BCrypt passwords, CSRF on, FK/UNIQUE/CHECK in the schema, indexes on FKs and on filter/sort columns, and layering into controller → service → repository. Business rules must be unit-testable without the UI, and tests must run with one command.
- **Legacy migration (RF-10)**: valid rows are migrated and invalid rows go to quarantine with a reason. Nothing is deleted or invented. For each sheet, migrated + rejected = source total. Expected for produção: 2,892 migrated and 3,108 rejected.

Requirement IDs (RL/LA/RF/RNF/RN/V) come from the requirements PDF and feed a traceability matrix that runs from the original requirement to the implementation and the test. Reference those IDs in code comments, tests and commits where it helps traceability. Points V-01..V-06 are open questions for the professor, so don't hard-code an answer to them without asking.
